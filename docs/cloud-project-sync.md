# Cloud project synchronization

`PUT /api/v1/integrations/cloud/projects/{UUID}` accepts only a dedicated, revocable `projects:sync` wiki key. Administrators issue one via the existing key API with `role: "projects:sync"`. The raw key is returned once; store it in the Cloud dashboard's private runtime environment. This key expires after 90 days and cannot read page/project/key APIs, change pages, administer keys, or sign into the browser. Existing keys retain their roles. A dedicated key is an explicit service credential; it is independent of a human's Cognito session or later group changes.

Send the version-1 Cloud projection (`schemaVersion`, `cloudProjectId`, `revision`, immutable `slug`/`code`, `name`, `description`, nullable HTTPS `appUrl`, `status`) and `Idempotency-Key: cloud-project-{UUID}-r{revision}`. Every field is required; unknown fields are rejected. Names are at most 80 characters; descriptions at most 20,000. Cloud UUIDs, positive safe-integer revisions, slug/code formats and HTTPS URLs are validated. The 128 KiB JSON body limit applies. Authenticated calls are limited to 120/minute/key; 429 supplies `Retry-After: 60`.

First creation returns 201, updates/replays 200. Response fields are exactly `schemaVersion`, `cloudProjectId`, `revision`, `resourceType: "project"`, `resourceId` (slug), `url` (configured public origin + `/projects/{slug}`). Identical latest-revision payloads return `Idempotency-Replayed: true`, across restarts and key rotation. Stale/conflicting revisions and immutable-identity changes return 409. Unrelated existing namespaces/directories are never adopted by name. The configured public origin determines URLs; incoming Host headers cannot change them.

The namespace metadata and durable Cloud identity/revision/canonical payload live together in one atomic `projects.json` update, serialized with normal project/page/key mutations. Directory creation is lazy from committed metadata, so an interrupted creation cannot leave mismatched project and ledger state. Key validity is rechecked inside the write queue. Only one Node process owns the data directory; CLI/operator mutations require stopping its owner first.

Rename updates the project's display metadata. Archive/restore update its Cloud status; pages, revisions and namespace identity remain available to signed-in readers. Native project deletion refuses linked namespaces. Project namespaces share the whole wiki's access policy; they are not per-project privacy boundaries.

Back up the entire data directory. For application rollback, disable Cloud's wiki worker and revoke its key first. Retain `projects.json` and all page directories. The prior application reads additional metadata without destroying pages; do not remove a Cloud-linked namespace through the older project's delete API. Forward recovery reuses the same identities and payloads. No data wipe, fuzzy adoption or page deletion is part of integration recovery.
